# ADR作成スキル（出典付き事実・公平な選択肢比較・留保付き推奨）

対象の資料や情報を読み込み、**議論の叩き台として機能するADR**を作成するスキル。単にテンプレートを埋めるのではなく、「出典付きの事実に基づき、選択肢を公平に並べ、起案者の推奨を留保付きで示す」文書を作ることがゴール。

書き始める前に、必ず次の2ファイルを読むこと。

- ADRの雛形: [references/template.md](references/template.md)
- 品質パターン集: [references/quality-patterns.md](references/quality-patterns.md)

## 使うとき / 使わないとき

- **使う**: 技術・アーキテクチャ・方針に関する意思決定を文書化するとき。決定済みの記録だけでなく、これから議論するための「叩き台（Proposed）」の作成にも使う。
- **使わない**: ADRの体裁を取らない設計書・解説資料（→ doc-format）、既存設計のレビュー（→ goal-oriented-design-review）、既存ADRの誤字修正など軽微な変更。

## 作業フロー

### Step 1: 論点とステータスの確定

1. **「何を決めるのか」を1文で言えるまで具体化する。** 「認可（誰がどの機能を実行できるか）をどうモデル化するか」のように、決定対象を明確にする。曖昧な場合はユーザーに確認する。
2. **ステータスを確認する**: 提案中（Proposed）＝議論の叩き台か、承認済み（Accepted）＝決定の記録か。指定がなければ「提案中／議論の叩き台」とする。
3. **起案者・日付・関連資料**を確認する（起案者はユーザー本人がデフォルト。ただし明示指定があればそれに従う）。

### Step 2: 資料の読み込みと事実抽出

指定された入力ソースをすべて読み込む。ソース種別ごとの手段:

- **Confluence ページ**: `confluence_get_page`（URLのページID指定）、関連ページは `confluence_search` / `confluence_get_page_children`
- **Slack スレッド**: `get_conversation_replies` / `search_messages`
- **Jira チケット**: `get_issue`
- **リポジトリ内ドキュメント・コード**: Read / Grep / Glob（量が多ければ Explore サブエージェント）
- **ユーザーからの口頭情報・議論メモ**: 会話内容をそのまま事実ソースとして扱う（出典は「〇〇さんとの議論（YYYY-MM-DD）」等と記録）

読みながら以下を抽出する。**すべての事実に出典を付ける**（ページ名・日付・リポジトリパス・会議名など）。

- 決定の背景・きっかけ（なぜ今この決定が必要か）
- 前提となる事実（確定事項と、推定・未確認事項を**区別**する）
- ステークホルダーと決定権（誰が要件を握り、誰が最終決定するか）
- スケジュール制約（日付で定量化する）
- 他チーム・他システムの関連計画（二重開発・依存関係の芽）
- 既存の類似実装・先行事例（選択肢の裏付けになる）

### Step 3: 決定ドライバの導出

資料と会話から**評価軸（決定ドライバ）を5〜7個程度**導出する。例: 要件の不確実性への強さ、拡張性、実装・運用コスト、監査・説明可能性、既存資産の活用、他チームロードマップとの整合、リリース時期への適合。

ドライバは後の選択肢の Pros/Cons と対応させるので、**この決定で本当に効く軸だけ**に絞る。

### Step 4: 選択肢の列挙

**最低でも2〜3案、できれば技術案に加えて組織的な選択肢も含めて**列挙する。

- 技術的な選択肢（例: 固定ロール型 vs 汎用RBAC型 vs ハイブリッド）
- **Build vs Borrow vs Buy**: 自前で作る / 他チーム・既存基盤に乗る / SaaS・既製品を使う / そもそも作らない
- 各選択肢に **Pros / Cons** を付ける。Pros/Cons は Step 3 のドライバと対応させる（どのドライバに効き、どのドライバで劣るか）。
- 推奨する選択肢はタイトルに「（起案者推奨）」を明記する。ただし**他の選択肢を弱く見せる書き方をしない**。各案のProsは、その案の支持者が書いたつもりで書く。

### Step 5: 推奨の形成

- **推奨**: どの選択肢を推すかを明確に。可能なら「段階的パス」（例: まずBの最小構成 → Cを重ねる → 将来Dへ移行できる余地を残す）として、**可逆性・移行余地**を織り込む。
- **根拠**: ドライバに紐づけて説明する。スケジュール・リスクは日付・数値で示す。
- **公平な留保**（省略不可）: 自分の推奨が誤りうる条件、別の選択肢が勝つ可能性、この ADR 単独で決められないこと（決定権者・すり合わせ先）を明記する。確証バイアスを抑えるための最重要セクション。

### Step 6: 影響・実施事項・再評価条件

- **影響（Consequences）**: ポジティブ / ネガティブ・受容するトレードオフ。
- **実施事項（Follow-ups）**: 優先度を付け、すり合わせる相手・確認事項を具体名で書く。「【最優先】」等のマーカーを使う。
- **再評価条件**: この決定を見直すトリガーを明文化する（「〇〇が確認できた場合は選択肢Dに切り替える」など）。

### Step 7: 付録と出力

- **付録**: 選択肢の裏付けとなる証拠（既存システムのデータモデル、調査結果など）を置く。図は mermaid のコードブロックで書く（Confluence の mermaid マクロにそのまま貼れる）。推定を含む場合は注記する。
- **出力**: ローカルの Markdown ファイルに書き出す。ファイル名は英語 kebab-case（例: `adr-authorization-model.md`）。出力先の指定がなければユーザーに確認する（迷ったらカレントディレクトリ）。
- Confluence に掲載する場合のページタイトル規約は **`YYYY/MM/DD NN <トピック> ADR`**（例: 「2026/08/05 04 認可モデル ADR」）。利用可能な Confluence MCP ツールは読み取り専用のため、**掲載は手動貼り付け**になる旨をユーザーに伝える。

## セルフレビューチェックリスト

- [ ] 「何を決めるのか」が1文で書かれているか
- [ ] 冒頭に文書の位置づけ（叩き台か決定か、誰との議論用か）が blockquote で宣言されているか
- [ ] 前提事実にすべて出典が付いているか。事実と推定が区別されているか
- [ ] ステークホルダーと決定権（誰が最終決定するか）が明示されているか
- [ ] スケジュール制約が日付で定量化されているか
- [ ] 決定ドライバが列挙され、各選択肢の Pros/Cons と対応しているか
- [ ] 選択肢に Build/Borrow/Buy の観点が含まれているか（該当する場合）
- [ ] 「公平な留保」があるか（推奨が誤りうる条件・決定権者への言及）
- [ ] 実施事項に優先度と相手（具体名）があるか
- [ ] 再評価条件が明文化されているか
- [ ] mermaid はレンダリング可能な構文か
- [ ] 出力ファイル名は英語 kebab-case か

## 行動指針

- すべて日本語で書く（英語指定がある場合を除く）。
- **中立性を最優先する。** ADR は説得の文書ではなく、意思決定の材料を公平に並べる文書。推奨は示すが、必ず留保とセットにする。
- **書かれていないことを埋めない。** 資料にない事実を創作しない。不明点は「未確認」「要確認」として実施事項に落とす。
- 議論の叩き台として使われることを想定し、読み手（決定権者・関係チーム）がそのまま会議に持ち込める密度にする。
