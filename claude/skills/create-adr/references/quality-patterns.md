# ADR 品質パターン集

「テンプレートを埋めただけのADR」と「議論の叩き台として機能するADR」の差を作る8つのパターン。

## 1. 出典付き事実

前提となる事実には**必ず出典**を付ける。読み手が事実の鮮度と信頼性を検証できるようにする。

- 良い例: 「**自チームで想定されている具体ロール（YYYY-MM-DD のふりかえり）**: 4種の事前定義ロール」
- 良い例: 「`doc/system-design/.../xxx.md`（認証・認可ポリシー）に機能単位 RBAC の方針が記載済み」
- アクセス状況も事実として書く: 「参考システムの生ソースは閲覧申請中。分析リポジトリはアクセス取得済み」
- 悪い例: 「関係者はロールを事前定義する想定らしい」（誰が・いつ・どこで、がない）

## 2. 事実と推定の区別

スキーマ・仕様の読み解きで推定した箇所は明示的に注記する。

- 良い例: 「`TABLE_A.COLUMN_X` の参照関係は**命名からの推定**（スキーマ上に明示 FK 制約はない）」
- 未検証の前提は「〜かは未検証」「〜の可能性がある」と書き、確認タスクを実施事項に落とす。

## 3. ステークホルダーと決定権の明示

「誰が要件を握り、誰が最終決定し、誰とすり合わせるべきか」を具体名（人名・チーム名・役割）で書く。ADR が宙に浮くのを防ぐ。

- 良い例: 「要件を詰めるメインは 〇〇さん。最終決定は △△さん（PL）と握る見込み」
- 良い例: 「この判断は □□チーム（担当マネージャー）とのすり合わせ次第であり、本 ADR 単独では決められない」

## 4. 制約の定量化

スケジュール・リスクは日付・数値で示す。「タイト」「余裕がない」だけで終わらせない。

- 良い例: 「基盤チームの機能構築は **YYYY-11〜12** の予定で、自チームの 1st リリース（**翌年03**）に対して余裕が小さい」

## 5. 公平な留保（確証バイアス抑制）

推奨セクションに「自分の推奨が誤りうる条件」を必ず併記する。ADR は説得ではなく意思決定の材料。

- 良い例: 「関係者は A（事前定義ロール）を想定している可能性が高く、B/C は自由度を足す提案。初期コストは A より大きい」
- 良い例: 「**D が最も筋が良い可能性**もある（全社方針と一致）。D が要件・スケジュールを満たせるなら、自前実装は最小化すべき」
- 良い例: 「要件が『少数固定ロールで恒久的に足りる』なら A で十分な可能性も残る」

## 6. 段階的・可逆な推奨

単一案の押し付けではなく、移行パスと可逆性を織り込んだ推奨にする。将来の選択肢を殺さない設計制約まで導出できるとよい。

- 良い例: 「当面は選択肢 B の最小構成を持ち、C の標準テンプレートを重ね、将来 D へ移行できる余地を残す」
- 良い例: 「B を作り込みすぎると D への移行時に無駄になるため、**対象ロジックは一箇所に集約し、データの供給元を後から差し替えられる**設計にしておく（B を『D への踏み台』として作る）」

## 7. Build / Borrow / Buy の選択肢

技術案の比較だけで閉じない。「他チームの機能に乗る」「SaaS を使う」「そもそも作らない」という組織的選択肢を対等に並べる。

- 例: 自前実装のバリエーション（選択肢 A〜C）に対し、「別チームが構築予定の共通基盤に乗る」選択肢 D を対等に検討する。二重開発の回避・SSoT 一元化という全社観点を Pros に、他チームのスケジュールへの依存・自チーム固有要件の未検証を Cons に。

## 8. 決定ドライバと Pros/Cons の対応

決定ドライバ（評価軸）を先に列挙し、各選択肢の Pros/Cons がどのドライバに効くかが読み取れるようにする。

- 例: ドライバ「二重開発の回避」→ 共通基盤案の Pros、ドライバ「リリース時期への適合」→ 同案の Cons、ドライバ「要件の不確実性への強さ」→ 柔軟型の Pros / 固定型の Cons。
- ドライバに対応しない Pros/Cons が多い場合、ドライバの選定か選択肢の分析のどちらかが甘い。

## アンチパターン

- **結論ありきの選択肢**: 推奨案以外の Pros が薄い・雑。各案の Pros はその案の支持者が書いたつもりで書く。
- **出典のない「〜と思われる」の連発**: 事実・推定・意見が混ざり、議論の土台にならない。
- **実施事項が抽象的**: 「関係者と調整する」ではなく「誰と・何を・いつまでに」。
- **再評価条件がない**: 決定が固定化し、状況が変わっても見直されない。
- **資料にない事実の創作**: 埋まらないセクションは「未確認」として実施事項に落とす。
